# 二次开发约定与扩展点对照表

[English](customization.md) | 中文

本参考帮助贡献者选择 DSH 二次开发的扩展点，区分硬规则与默认建议，并处理例外。它补充已有规范，不替代原规范，不新增审批或检查流程。

## 硬规则、默认建议与例外

| 级别 | 含义 |
|---|---|
| 硬规则 | 遵守当前版本已有的运行、依赖、安全和兼容要求，以及本次已确认的产品行为。具体规则保留在下方链接的原文中。 |
| 默认建议 | 已有机制适合需求时优先复用。允许新增组件、调整布局和修复公共实现，不要求先把配置方案逐个试失败。 |
| 例外路径 | 默认方式不合适时，说明具体缺口、修改归属、受影响消费方和验证方式，选择更直接的实现。例外不等于绕过有效的安全或兼容要求。 |

## 扩展点对照表

| 需求 | 默认入口 | 何时调整实现 |
|---|---|---|
| 功能选配、公司默认配置、启动组合 | Profile、组合包和配置 patch | 配置无法表达所需能力时，新增插件或修改能力拥有者。公共缺陷直接修复，不用 overlay 长期掩盖。 |
| 公司名称、Logo、欢迎区 | 品牌插件及 sidebar／hero Slot | 现有位置不满足已确认体验时，可补 Slot 或调整布局。页面标题、首帧等另查构建与启动入口。 |
| 主色、背景、按钮与选中态 | 主题插件 `ctx.theme.overrideTokens`，组件消费语义 token | 缺少语义或控件能力时，扩展主题或公共组件；局部布局留在组件。使用 token 不等于品牌交付完成。 |
| 公司身份与退出入口 | 服务端身份和退出能力，客户端账号界面或相应 Slot | HTML 启动数据、form、API 按实际需求选择。公司身份与模型身份分别定义，不因存在公司登录就自动隐藏模型账号。 |
| 业务页面、结果卡、操作入口 | 客户端插件、Slot 和现有 primitives | 业务专用组件留在功能包；适合共享的控件进入公共组件。允许新增布局，不为一次性需求强建通用机制。 |
| 业务能力、策略与协作 | 服务、事件、注册接口 | 扩展点缺失或拥有者存在缺陷时，补接口或修改实现；不把“插件优先”解释为“核心不可修改”。 |

## 采用依据与例外处理

普通改动复用已核验的文档或参考实现即可。首次使用机制、版本变化、资料冲突或出现明显绕路方案时，再核对当前版本源码、随仓文档及对应上游资料；不要求每次开发重复搜索外网。

调整公共实现时，以下说明通常已经足够：

> 当前场景是……；现有入口缺少……；拟在……中调整；影响……；通过……验证。

一个明确场景即可构成依据，不强求多个调用者。普通实现自主推进；改变长期职责、共享扩展机制或已约定行为时，按已有规则处理，复用已确认的判断。

## 按改动范围验证

依据现有[测试规范](testing.zh.md)，为受影响行为选择验证证据。

| 改动 | 需要提供的证据 |
|---|---|
| 文案 | 相关中英内容、显示与可访问名称 |
| 样式或组件 | 受影响状态，以及相关明暗主题、窄屏和键盘操作 |
| 品牌或装配 | 实际启用组合和约定用户入口，覆盖本次交付的页面与状态 |
| 能力或共享机制 | 受影响消费方、失败路径及相关生命周期行为 |

源码存在、构建通过、部署完成和用户入口验证分别报告。检查优先复用现有机制；发现覆盖缺口时补缺口，不另建重复清单。

具体规范保留在[架构与装配](architecture.zh.md)、[客户端规则](../packages/client/AGENTS.md)、[Slots](subsystems/slots.zh.md)和[样式规范](web-styling.zh.md)中。
